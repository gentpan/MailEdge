# MailEdge QA Status — 2026-08-09

This report records verified evidence for the `v0.2.3` release candidate and
the `v0.2.2` production baseline. It does not replace the release gate in
`docs/QA-MATRIX.md`.

## Executive status

**Current decision: Go for the `v0.2.3` source release; No-Go for unattended
destructive Cloudflare rollout tests.**

The local application baseline and production edge hardening checks pass. Fresh
install, repeat install, upgrade, failure recovery, complete uninstall, backup
restore and rollback still require an isolated Cloudflare account before those
destructive paths can be promoted to unattended production automation.

## Verified production infrastructure

Production host details are intentionally retained outside the public source
repository.

- The deployer listens only on `127.0.0.1:8788`; direct public IPv4 access is
  refused and IPv6 does not expose the application port.
- `mailedge.sh` and `mailedge.io` return HTTPS 200; their `www` hosts redirect
  to the canonical bare domain.
- The systemd service is enabled and active with restart policy enabled.
- Caddy configuration validates and reloads cleanly.
- HSTS, `nosniff`, frame denial, strict-origin referrer policy, and restrictive
  browser feature policy are present on all four public hosts.
- Production source and configuration backups were verified before each P0
  change; their host-specific paths are intentionally retained outside this
  public repository.

The last deployment used a verified release staging directory and an atomic
directory switch with a tested host-local rollback point. Runtime validation confirmed the
OAuth `__Host-` state cookie, same-origin/cross-origin behavior, CLI Token
compatibility, zero third-party font or analytics imports on `mailedge.sh`,
unchanged version/statistics APIs, and zero post-start error logs.

CSP is intentionally pending. Nuxt currently emits an inline import map, so a
policy must first be validated in browsers to avoid silently breaking the OAuth
or deployment UI.

## Release blockers

The following tests require a dedicated, disposable Cloudflare account and
must not run against production credentials or customer data:

1. Fresh install with R2 and KV, R2-only, KV-only, and neither storage usable.
2. Idempotent repeated install with existing Worker, D1, storage, and secrets.
3. Upgrade from `v0.2.2` to `v0.2.3`, with before/after D1 rows, Durable Object
   messages, R2/KV object checksums, and secret-name comparison.
4. Forced interruption at every setup phase and recovery without duplicate
   deployment counts or regenerated encryption/session secrets.
5. Complete uninstall with nested/Unicode/large storage inventories, including
   storage failure injection that proves Worker and D1 are preserved.
6. OAuth denial, expired/replayed state, popup closure, token revocation,
   multiple accounts, server restart, CSRF/origin checks, rate limits, and
   credential-leak audit.
7. Backup restore and previous-release rollback drills.
8. Full-page visual snapshots beyond the authentication shell in Firefox and
   WebKit, plus a 24–48 hour canary. Browser smoke and serious/critical
   accessibility scans already pass in Chromium, Firefox, and WebKit.

## Go criteria

Promote the destructive installer matrix to unattended production use only when
every blocker above is evidenced, P0 and P1 are both zero, application and
storage data differences after upgrade are zero, a rollback succeeds, and the
canary completes without an unresolved P0/P1 incident.
